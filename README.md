## 🧱 How I Build Applications

### 1. Understand the Requirement

- Identify the user and the business problem.
- Clarify the expected input and output.
- Identify permissions and edge cases.
- Confirm what should happen when data is missing or invalid.
- Keep the first implementation focused on the actual requirement.

### 2. Plan the Data

- Identify the entities involved.
- Define primary keys and relationships.
- Decide which fields are required.
- Add constraints where the database should enforce integrity.
- Plan migrations so schema changes are repeatable.

### 3. Implement the Backend

- Define routes and HTTP methods.
- Validate incoming data.
- Check authentication and authorization.
- Keep business rules understandable.
- Use transactions for operations that must succeed or fail together.
- Return appropriate success and error responses.

### 4. Build the Interface

- Use reusable layouts and components.
- Keep forms understandable.
- Show useful validation feedback.
- Support common screen sizes.
- Avoid relying only on client-side validation.
- Make loading, empty, and error states clear.

### 5. Test the Workflow

- Test the normal path.
- Test missing and invalid input.
- Test permissions using different user roles.
- Test relationship and deletion behavior.
- Verify that unrelated modules still work.
- Review logs if an error occurs.

### 6. Deploy Carefully

- Back up important data where appropriate.
- Keep secrets in environment configuration.
- Review production settings.
- Run required migrations carefully.
- Clear or rebuild caches only when appropriate.
- Verify the updated workflow after deployment.

## 🔌 API Development Practices

When working on an API, I aim to make the request and response contract clear.

- Choose HTTP methods that match the operation.
- Validate incoming parameters and request bodies.
- Use suitable HTTP status codes.
- Return predictable JSON structures.
- Protect private endpoints with authentication.
- Apply authorization to the specific resource being accessed.
- Avoid returning secrets or unnecessary internal details.
- Handle missing records and invalid input gracefully.
- Document required fields and response examples.
- Test both successful and unsuccessful requests.

### Common HTTP Status Codes

| Code | Meaning | Typical use |
| --- | --- | --- |
| 200 | OK | Successful request |
| 201 | Created | Resource created successfully |
| 204 | No Content | Successful request with no response body |
| 400 | Bad Request | Request cannot be processed as submitted |
| 401 | Unauthorized | Authentication is missing or invalid |
| 403 | Forbidden | Authenticated user lacks permission |
| 404 | Not Found | Resource does not exist or is not accessible |
| 422 | Unprocessable Content | Validation failure |
| 429 | Too Many Requests | Rate limit reached |
| 500 | Internal Server Error | Unexpected server-side failure |

## 🗄️ Database and SQL Practices

MySQL is an important part of my everyday development work.

### Core Areas

- Table design and relational modeling
- Primary and foreign keys
- One-to-one, one-to-many, and many-to-many relationships
- Joins and aggregate queries
- Filtering, sorting, and pagination
- Indexing fundamentals
- Transactions and data integrity
- Schema migrations
- Query debugging

### Query Quality Checklist

- Select only the columns needed.
- Add filters that reflect the intended data scope.
- Use parameter binding rather than concatenating untrusted values.
- Check whether indexes support common filters and joins.
- Avoid repeating the same query unnecessarily.
- Use eager loading when retrieving related Eloquent models.
- Paginate large result sets.
- Inspect query behavior before assuming the database is the bottleneck.

### Data Integrity

- Use foreign keys when they fit the domain.
- Choose deletion behavior deliberately.
- Validate business rules before changing records.
- Use transactions for multi-step writes.
- Consider duplicate requests and retry behavior.
- Preserve important historical records when the business requires an audit trail.

## 🔐 Security Mindset

Security is part of application design, not a final decoration.

- Validate and normalize incoming data.
- Use Laravel's CSRF protections for state-changing web forms.
- Use parameterized database access through Eloquent or query builder.
- Escape output appropriately in templates.
- Store passwords using secure password hashing.
- Keep credentials and API keys out of Git repositories.
- Check permissions on the server for every sensitive operation.
- Restrict file uploads by type, size, and expected use.
- Avoid exposing stack traces or secret configuration in production.
- Apply rate limits to sensitive endpoints where appropriate.
- Keep dependencies and the runtime updated.
- Review authorization and tenant boundaries during testing.

> A hidden button is not an authorization mechanism. The server must enforce who can view or change each record.

## ⚡ Performance and Reliability

I approach performance by measuring the actual bottleneck before making changes.

- Review slow queries and repeated database access.
- Use eager loading to reduce N+1 query patterns.
- Paginate large tables and result lists.
- Cache only data that is appropriate to cache.
- Keep cache invalidation and tenant boundaries in mind.
- Move suitable long-running work to queues.
- Avoid loading unnecessary relationships or columns.
- Use logs to diagnose recurring failures.
- Test behavior with realistic data volumes.
- Prefer simple, measurable optimizations over premature complexity.

### Performance Review Questions

- Is the page making too many database queries?
- Are queries filtering on indexed columns where appropriate?
- Is the application loading every record at once?
- Is an external service delaying the request?
- Is repeated work suitable for caching?
- Would a queue improve response time?
- Has the change been measured before and after?

## 🧪 Testing and Debugging Workflow

When something fails, I try to reproduce the problem before changing code.

1. Record the exact action that triggers the issue.
2. Check the error message and relevant logs.
3. Reproduce the issue in a safe development environment.
4. Trace the request through the route, middleware, controller, and model.
5. Inspect the input and database assumptions.
6. Identify the smallest likely cause.
7. Make a focused fix.
8. Test the original failure case.
9. Test nearby workflows that might be affected.
10. Document any operational step needed after deployment.

### Common Debugging Tools

- Laravel application logs
- Browser developer tools
- Network request inspection
- MySQL query inspection
- Postman
- PHP error output in development
- Git diff and history
- Small reproducible test cases
